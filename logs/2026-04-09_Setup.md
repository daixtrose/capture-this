## Font Bundling Fix (2026-04-09)

### Problem

After `pnpm slidev build`, the WOFF2 font files were **not included** in `dist/`. The `@font-face` CSS declarations were present in the compiled CSS (`dist/assets/index-*.css`) but the actual `.woff2` files were missing.

### Root Cause

Fonts were originally stored at `talk/fonts/` and referenced via relative paths (`url('../fonts/...')`) from the theme CSS at `talk/daixtrose-basic/styles/fonts.css`. Vite did not resolve these relative paths from the theme subdirectory as static assets.

### Solution

1. **Moved** `talk/fonts/` → `talk/public/fonts/` (Vite copies everything from `public/` into `dist/` as static assets)
2. **Updated** `@font-face` `src:` URLs from relative (`../fonts/...`) to absolute (`/fonts/...`)

### Verification

After rebuild: `find dist -name "*.woff2"` confirmed all 17 WOFF2 files are now present in `dist/fonts/`.

## Open Questions

### Monaco Editor + C++ Compiler

> **User:** Is it possible to connect the Monaco Editor to a C++ compiler (in a container or one running in the web browser)?

**Status: Researched.** Based on the complete Slidev documentation reading:

#### How It Works in Slidev

Slidev has a **custom code runner API** via `./setup/code-runners.ts`:

```ts
import { defineCodeRunnersSetup } from '@slidev/types'

export default defineCodeRunnersSetup(() => {
  return {
    async cpp(code, ctx) {
      // Send code to a backend compiler, get result back
      const result = await executeRemotely(code)
      return { text: result }
    },
  }
})
```

Then in slides, use `{monaco-run}` on C++ code blocks:

````md
```cpp {monaco-run}
#include <iostream>
int main() {
    std::cout << "Hello!" << std::endl;
}
```
````

This gives a Monaco editor with a **Run** button and inline output below the code block.

#### Backend Options

1. **Compiler Explorer (Godbolt) API** — `https://godbolt.org/api/compiler/<id>/compile`
   - Free, public API. Supports many compilers (GCC, Clang, MSVC)
   - Supports compilation + execution
   - Requires network access; suitable for online presentations
   - Example: POST JSON with `source`, `options.userArguments`, `compilerOptions.executorRequest: true`

2. **Local Docker container** — Run `gcc`/`clang` in a container with a small HTTP API
   - Fully offline, no network dependency
   - Could use a simple Express/Flask server wrapping `g++ -o /tmp/prog /tmp/code.cpp && /tmp/prog`
   - Ideal for conference environments with unreliable WiFi
   - Security considerations: sandbox the compiler, set resource limits

3. **WebAssembly-based C++ compilation**
   - Projects exist (e.g., experimental Clang-WASM) but are immature for full C++ standard library support
   - Not recommended for production use yet

#### Recommended Approach

Use **Compiler Explorer API for development** (easy, full-featured) with an optional **local Docker fallback** for offline conference use. The code runner in `setup/code-runners.ts` can check `localhost` first and fall back to Godbolt.

#### Additional Notes from Docs
- `{monaco-run} {autorun:false}` — manual run only (good for live demos)
- `{monaco-run} {showOutputAt:'+1'}` — show output on next click
- `monacoRunAdditionalDeps` headmatter for extra dependencies
- Monaco editor height: `{height:'auto'}` for auto-growing editor
- `editorOptions: { wordWrap:'on' }` for code that wraps

### C++ Compiler Flags for Cross-Standard Demos (2026-04-10)

> **User:** Can I use g++'s `-std=` flag to show different compiler reactions on the same code?

**Yes — this is exactly the right approach.** A single compiler (e.g., `g++-15`) with different `-std=c++11`, `-std=c++14`, `-std=c++17`, `-std=c++20` flags reveals how the standard evolution changed the behavior of lambda capture expressions.

**Comprehensive behavior table:**

| Expression     | C++11           | C++14           | C++17           | C++20                     |
| -------------- | --------------- | --------------- | --------------- | ------------------------- |
| `[this]`       | ✅ pointer       | ✅ pointer       | ✅ pointer       | ✅ pointer                 |
| `[*this]`      | ❌ error         | ❌ error         | ✅ copy          | ✅ copy                    |
| `[=]`          | ✅ implicit this | ✅ implicit this | ✅ implicit this | ⚠️ deprecated (this)       |
| `[&]`          | ✅ implicit this | ✅ implicit this | ✅ implicit this | ✅ implicit this           |
| `[=, this]`    | ❌ error         | ❌ error         | ✅ explicit this | ✅ explicit this (no warn) |
| `[=, *this]`   | ❌ error         | ❌ error         | ✅ copy          | ✅ copy                    |
| `[self=*this]` | ❌ error         | ✅ init capture  | ✅ init capture  | ✅ init capture            |

**Key teaching points for the talk:**
1. **C++11→C++14:** Init captures arrive (`[self=*this]` workaround becomes possible)
2. **C++14→C++17:** Direct `[*this]` and `[=, this]` / `[=, *this]` become legal
3. **C++17→C++20:** `[=]` inside member functions triggers deprecation warning (implicit `this` capture is now considered dangerous)

**Demonstration strategy:**
- Same `.cpp` file compiled with `-std=c++11`, `-std=c++14`, `-std=c++17`, `-std=c++20`
- Show compiler output (errors, warnings, success) side by side
- Highlights the *evolution* of the standard, not just the final state

### GCC 15 Compilation Results (2026-04-10)

All 24 compilations (6 examples × 4 standards) pass. GCC 15.2 is **permissive** — it accepts future-standard features in older modes with warnings instead of hard errors.

**Warning matrix (clean = no warnings):**

| Example | C++11 | C++14 | C++17 | C++20 |
|---|---|---|---|---|
| 01 `[this]` | clean | clean | clean | clean |
| 02 `[*this]` | `-Wc++17-extensions` | `-Wc++17-extensions` | clean | clean |
| 03 `[self=*this]` | `-Wc++14-extensions` | clean | clean | clean |
| 04 `[=]` implicit | clean | clean | clean | `-Wdeprecated` |
| 05 `[=, this]`/`[=, *this]` | `-Wc++20-ext` + `-Wc++17-ext` | `-Wc++20-ext` + `-Wc++17-ext` | `-Wc++20-ext` | clean |
| 06 dangling | clean | clean | clean | clean |

**Key observation for the talk:** GCC 15's permissive behavior is pedagogically useful — the warnings clearly state which standard introduced each feature, e.g., `'*this' capture only available with '-std=c++17'`. Adding `-Werror` would turn these into hard errors for strict compliance testing.
